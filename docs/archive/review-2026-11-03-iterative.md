## 第一轮：修复 Gemini 原生生图绕过并发限制

**问题与影响**：原有 `image_max_concurrency` 仅在 `chat_api._call_upstream` 内生效。
Claude 复用该入口，因而受到保护；原生 Gemini 的 Express `_passthrough_request`
和 Cookie `_handle_native_request` 只使用全局生成闸，能够绕过图片内存闸。
同一进程混合使用多种协议时，管理员设置的生图上限不能约束全部图片生成。

**修复**：提取 `admission.run_with_image_limit`，三个生成入口共享同一个图片计数器。
原生只对 `generateContent` / `streamGenerateContent` 启用图片闸，
文本生成及 `countTokens` 等操作不占图片名额。
响应为流时，租约随迭代器保持到 EOF 或关闭；整包返回、初始化异常和取消均归还名额。

**复现和复核**：在图片名额已满时，两个原生通道、两种生成动作原先均继续进入处理流程；
修复后均在开始上游工作前抛出容量错误。另验证流的正常结束、未开始即关闭、
重复关闭、非流式返回、初始化异常和取消。原有图片生命周期 18 项回归通过。

## 第二轮：修复续传超窗后新旧生成重叠

**问题与影响**：`ResumableStore.cancel_generation` 发出取消前就从 `_pumps` 移除任务。
取消信号并不表示连接已经关闭；当旧任务还在 `finally` 里清理连接时，相同请求重来，
替换逻辑找不到旧任务，跳过原有等待步骤并开始新生成，出现资源和上游消耗重叠。

**修复**：保留取消中任务的索引，由原有任务完成回调在真正结束后移除。
相同请求替换时可以找到旧任务，并继续执行既有的最多 5 秒清理等待。
超过等待边界仍沿用原有容量错误和新占位撤销规则，避免无限等待。

**复现和复核**：用事件精确暂停旧任务的清理阶段；修复前替换立即返回，
修复后必须在释放清理事件后才能返回新生成占位。旧缓冲继续保留 HTTP 410 终态。
原有续传交付 23 项回归通过，包括窗口内重连、轮询延长窗口和超窗取消。

## 第三轮：减少 Cookie 原生 Part 计量的临时内存

**问题与影响**：`NativeAssembler.feed` 用
`len(json.dumps(part, ensure_ascii=False).encode("utf-8"))` 检查字节预算，
会为图片 Base64 创建整份 JSON 字符串与 bytes 临时副本。
实际发送时还需要再次序列化，计量阶段的全量分配属于额外开销。

**修复**：新增 `_part_json_size`。大字符串以 64 Ki 字符切片计算转义后的 UTF-8 长度，
其余结构交给标准 JSON 编码器计量。按切片扣除引号，再加上结构中的引号和分隔符，
结果与原来的 JSON 计量完全一致。原始 Part 不变，响应预算和累计上限继续生效。

**复现和复核**：2 MiB Part 的计量原先会物化超过 2 MiB 的单个 JSON 字符串；
新回归要求计量阶段任何一次序列化产物小于 512 Ki 字符。
中文、emoji、换行、引号、反斜杠、控制字符、切片边界和嵌套工具参数均与原计量逐字节对照。
另验证单 Part 超限和多 Part 累计超限仍会拒绝响应。

离线基准（Python 3.12.14，32 MiB Base64 Part，5 次时间测量取中位数）：

| 指标 | 原实现 | 新实现 | 变化 |
| --- | ---: | ---: | ---: |
| 计量结果 | 33,554,485 bytes | 33,554,485 bytes | 完全一致 |
| 计量耗时 | 94.95 ms | 65.66 ms | 减少约 31% |
| 计量临时 Python 分配峰值 | 72.00 MiB | 0.126 MiB | 减少约 99.8% |

这是 `tracemalloc` 测得的**计量环节额外分配**，不含输入构造、实际发送、
整个进程 RSS 或端到端吞吐；不能据此声称服务总内存只有 0.126 MiB。

复跑命令：

```bash
python scripts/benchmark_native_part_size.py --megabytes 32 --repeats 5
```

## 第四轮：复查并修复图片流的诊断上下文丢失

**问题与影响**：图片闸为避免重复计数使用 `traced=False`，其租约的 `trace` 为 `None`。
`LeasedIterator` 在每次读取与关闭时仍把 `current_trace` 设为该值，
导致内层图片流失去请求身份，上游读取阶段的日志、首回复和重试事件可能无法关联到监控记录。
此问题在原有 OpenAI 图片包装中已经存在，统一入口后的复核进一步确认两个原生通道同样受影响。

**修复**：迭代器创建时捕获所属请求的追踪上下文；辅助闸继承上下文，
计数与结束事件仍仅由拥有追踪租约的全局闸负责。读取和关闭都使用捕获的身份。

**复现和复核**：在两个原生通道分别验证正常读取和提前关闭。
修复前四种组合的底层迭代器都观察到空追踪；修复后身份保持一致，全局生成状态正常结束。
原有请求追踪 14 项回归通过。
