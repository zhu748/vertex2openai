# Cookie OpenAI 工具参数增量与分层诊断

用户的 `trace-9c2cacd18110a601` 不再出现工具分片校验错误，但直到请求开始后 315.8 秒才记录首个上游对象和工具调用，约 0.2 秒后结束。第二次上游调用约等待 241 秒后返回 429，第三次调用约 65 秒后成功。原日志无法证明 Cookie 私有接口实际发送过 `partialArgs`，也无法区分“早有正文数据但 JSON 尚未完整”和“上游一直没有发送数据”。

代码复查还发现独立的交付问题：此前 Cookie 的工具参数分片虽然能结束首回复计时，却仍通过 `ToolStreamAssembler` 合并为完整调用后才发给 OpenAI 客户端。这与客户端真正收到参数增量是两件事。

## 本轮实现

Cookie OpenAI 的原生自定义工具路径开启增量交付：

1. 首次函数名称通过 `delta.tool_calls[index].function.name` 发出，后续不重复名称。
2. 参数通过 `function.arguments` 的 JSON 字符串片段追加，客户端按 `index` 合并。
3. 上游 ID 已知时只发送一次；晚到的 ID 填入同一索引；上游始终缺少 ID 时，在完整参数校验后沿用已有稳定 ID 生成规则补齐。
4. 完成时保留调用签名及签名回放记录，不再把整份 arguments 再发一次。
5. 参数全部校验通过且有有效结束标记，才发送成功结束。已经发送工具增量后遇到网络、配额或参数错误，返回错误并停止，不重新发起可能混入旧前缀的另一轮生成。

这是标准工具参数流，不把函数参数强行改为普通正文。酒馆是否在工具生成途中展示参数，取决于客户端和工具扩展的渲染方式；服务端的参数增量、完整工具执行和页面正文展示需要分别判断。

## JSON 前缀的正确性与边界

追加式序列化器逐片转义字符串，不反复序列化已发出的整段参数；它支持布尔 false、数值 0、null、引号/反斜杠/换行、中文、分片代理项、并行调用、晚到调用 ID 和乱序数组元素。

原生 JSONPath 片段可能交错补写嵌套字段，不能猜测嵌套对象已经关闭。因此尚未确认完成的容器保持开放，后续外层兄弟字段必要时等到完整调用再输出。这样可以流式发送已知安全的前缀，同时保证拼接结果仍是正确 JSON。参数未闭合、数组缺口、无效数值与冲突仍报错，不输出成功的工具结束。

Gemini 原生桥接保持原有完整 Part 组装；Express、非流式/假流式及内部文本工具传输也不在此次参数增量路径内。

## 新诊断如何判断问题所在

每次 Cookie 上游调用记录独立计数，并在请求详情的 `cookie_tool_stream` 对象及时间线中保留：

| 诊断 | 能说明什么 |
| --- | --- |
| 参数流式是否已请求、首回复保护的实际值 | 配置是否真正发出；计时是否被关闭 |
| 上游响应头到达 | HTTP 响应是否已开始；不代表有模型输出 |
| 首段上游正文数据 | 文本读取已经开始；不代表 JSON 已完整 |
| 首个 JSON 对象 | 解析器已得到完整对象；仍可能只有空字段、错误或用量 |
| `fragment_parts` / `argument_fragments` | 实际观察到 `willContinue` / `partialArgs` 的 Part 和参数片段数 |
| `full_tool_parts` | 上游直接给出完整函数对象的次数 |

如果最终只有完整工具对象而没有分片，日志明确显示“本次上游仅返回完整工具对象，未观察到参数分片”。输入配置接受 `streamFunctionCallArguments` 并不能证明私有 GraphQL 响应支持返回这些字段。转换层不能提前生成上游没有发送的内容，也不会把已完整收到的对象拆几帧后称为上游分片。

这些诊断不调用首回复接受逻辑；早到的响应头、空 JSON 和原始文本仍不能取消首回复超时。日志只记录时间、计数和配置，不保存工具参数、生成正文、Cookie 或签名。
