# 图片内存专项复核（2026-11-03）

在上一轮工作区改动基础上，针对最近避免图片 OOM 的提交继续审查。
重点核对 `27f00a8`、`362116a`、`3458498`、`74b6ca7` 和相关调用链，
覆盖输入图、HTTP 收集、SDK 转换、非流式 JSON、OpenAI/Claude SSE、Gemini 原生桥接及慢客户端。

结论：已有的 Base64 分帧、续传绕过、并发闸和收集期释放确实减少了大图片副本；
继续复核仍找到五处可降低内存的环节，已落实修复并增加回归保护。

## 一、输入压缩仍复制整幅像素

`ImageOps.exif_transpose(img)` 默认返回新图片：即使没有 EXIF 旋转，也会复制完整像素。
外层 `with Image.open(...)` 又会保留原图至处理结束，因此透明合成、缩放和编码期间
仍多驻留一幅原始大图。只优化透明合成没有消除这个副本。

改用 `ImageOps.exif_transpose(img, in_place=True)`。不改变压缩尺寸、质量或透明合成顺序。
回归对全部 8 种 EXIF 方向比较最终 JPEG 字节，并断言压缩调用使用原位校正。

24MP RGBA 输入图的完整压缩路径，在独立子进程中测得新增峰值 RSS 中位数
**172.18 → 88.02 MiB**，输出 SHA-256 一致。

## 二、HTTP 整取结束时仍有全量复制

`read_limited_bytes` 原先以 bytearray 收集，再 `bytes(data)` 返回。
大图片响应在转换瞬间同时保留两份完整 HTTP body，即使后续解析会及时释放它们，
这一瞬时峰值仍可能触发容器 OOM。

改为 BytesIO 收集并返回 `getvalue()`。在项目使用的 CPython 中，完成后的不可变 bytes
可与内部缓冲共享，不再复制完整响应。Content-Length 预检、实际解压字节限制、
错误响应限制和流关闭责任保持原有行为。

32 MiB HTTP body 的额外 Python 分配峰值 **68.00 → 36.00 MiB**。
测试覆盖恰好到限额及多一个字节必须失败。

## 三、非流式响应仍经过整份 JSON 文本

之前已验证“提前 dumps 再 encode”不能显著改善内存，因为仍经过完整 JSON 文本、
编码器内部累积缓冲和最终 UTF-8 bytes。此次改变的是编码方式。

新增 `json_encoding.iter_json_bytes`：长字符串先以 64 Ki 字符切片，再逐片 JSON 转义及
UTF-8 编码；结构分隔符、字典键序、空白格式、Unicode、严格非有限数拒绝规则与标准编码一致。
`LargeJSONResponse` 将这些片段写入最终 BytesIO，仍继承 JSONResponse，保持状态码、
Content-Length、响应头和非流式协议语义。

接入位置：Express 巨型非流式正文、Cookie 生图整包、Gemini Cookie 原生生图整包、
Claude 大型非流式响应。Claude 在完成 OpenAI JSON 解析后还会释放中间响应，
减少与 Anthropic JSON 编码的驻留重叠。

32 MiB 正文的编码额外分配峰值 **72.00 → 36.18 MiB**。
最终 bytes 仍必须完整驻留；没有将非流式接口改成 SSE，也没有降低图片分辨率。

## 四、Cookie 原生图片事件仍生成巨帧

上一轮仅降低了 `NativeAssembler` 的大小计量内存，实际发送仍用整份 `json.dumps`
加 SSE 包装串，然后由 ASGI 再编码一次。OpenAI 的图片切片无法保护这条原生协议路径。

大 Part 现在通过上述编码器产生有界的网络片段。拼接后仍是**同一个完整 SSE 事件**，
或同一个 JSON 数组元素；`inlineData.data` 不会拆成多个模型 Part。
普通文本、工具与结束事件继续作为单个字符串帧输出，避免增加正常 token 流的网络写入次数。
编码片段之间不插入心跳。关闭在图片编码中途暂停的响应，会关闭原上游事件流并归还租约。

32 MiB 图片 Part 的 SSE 编码额外分配峰值 **96.00 → 0.257 MiB**。
回归验证 SSE 与 JSON 数组均只含一个完整图片对象、保留结束原因，并验证中途关闭。

## 五、Claude 队列按帧计数仍能积压整图

原有异步生产队列上限为 128 帧。大图片切成 256 KiB 后，队列仍能预读约 32 MiB，
与仍在上游生成器内的原图正文叠加，抵消部分惰性切片收益。

新增 `ByteBoundedQueue`，同时约束 128 帧和 **2 MiB 排队字节**。超出字节预算时阻塞
生产者，形成背压；正常短文本保留原来的帧数余量。超过预算的合法单帧可独占队列字节预算，
后续数据帧必须等待它出队，避免因单帧本身大于预算而死锁。

慢读者回归暂停在 `message_start` 后，原始计数队列会预读 **129** 个图片切片，
违反测试的 12 帧上限；新队列通过该上限。另覆盖取消等待时归还已预留字节、
单个超大帧通行、后续帧等待及关闭上游。

2 MiB 约束的是排队帧，不包括消费中的帧、分帧器缓冲和上游原始正文。

## 基准汇总

Python 3.12.14，JSON/HTTP 样本 32 MiB，时间取 3 次中位数：

| 环节 | 优化前额外峰值 | 优化后额外峰值 | 优化前耗时 | 优化后耗时 |
| --- | ---: | ---: | ---: | ---: |
| 24MP RGBA 输入完整压缩，子进程 RSS 增量 | 172.18 MiB | 88.02 MiB | 964.11 ms | 929.99 ms |
| 有界 HTTP 整取，Python 分配 | 68.00 MiB | 36.00 MiB | 25.93 ms | 17.88 ms |
| 非流式 JSON 编码，Python 分配 | 72.00 MiB | 36.18 MiB | 121.80 ms | 110.71 ms |
| 原生 SSE 编码，Python 分配 | 96.00 MiB | 0.257 MiB | 154.63 ms | 119.96 ms |

JSON 和 HTTP 数据通过标准编码或摘要比对；PIL 两版输出的 SHA-256 一致。
四项属于不同阶段、不同测量口径，不能相加当成单次请求或整个服务的内存节省。
Python 分配不包含已构造的输入样本或进程全部 RSS，时间也不是端到端模型响应耗时。

```bash
python scripts/benchmark_image_memory_review.py --megabytes 32 --repeats 3 --baseline-ref b1851e3

python scripts/check_project.py
```

## 验证边界与后续容量验证

本次没有真实 Google 凭据，也没有在真实 512 MiB 容器中压测完整 SDK/HTTP 链路。
已测量的改善不能保证任意尺寸、任意并发均不会 OOM。

仍需在目标部署验证：

| 场景 | 原因 |
| --- | --- |
| SDK 自身整取/解析超大图片 | 应用编码优化发生在 SDK 返回后，无法消除 SDK 自身的完整图片驻留 |
| 多客户端同时下载大型非流式响应 | 每个响应仍持有最终 bytes，慢连接会延长其驻留时间 |
| 多请求并行处理输入图片，同时生成输出图片 | 媒体线程和生成阶段的占用会叠加，单阶段基准不能替代容量测量 |
| 实际 HTTP 压缩、curl 预读和网络背压 | 本次验证使用离线流及固定图片，需结合目标传输栈测量 |

现有图片并发设置、64 MiB 上游预算及像素上限继续生效；本次没有提高这些边界。
也没有通过降低输出档位、图片分辨率或 JPEG 质量来取得上述基准收益。
