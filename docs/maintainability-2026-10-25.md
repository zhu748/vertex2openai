# 代码组织与可维护性重构记录

本轮目标是明确模块职责、减少入口函数的嵌套状态、改善源码阅读体验，并让结构约束可以持续检查。
先检查调用关系与现有回归，再进行三轮调整和复查。基线是本轮开始时的工作区，包含上一轮功能修复；
没有重置这些修复，也没有提交、推送或部署。

## 探查结果与验收标准

| 探查发现 | 验收标准 |
| --- | --- |
| 代理 URI 转换与子进程管理在同一模块 | 协议解析独立，原有公共入口可继续调用 |
| Cookie 原生桥接和探测引用 OpenAI 适配器的私有传输函数 | 共用传输模块提供直接入口，不反向依赖适配器 |
| Cookie 与 SDK 的主要生成入口包含多个嵌套函数，通过闭包共享客户端、计时和重试状态 | 每次请求创建独立对象，字段和交付方法可直接定位 |
| SDK 响应转换、网络调用与重试混在一起 | 转换模块与调用编排分别维护 |
| SDK 消息转换把所有角色和合并规则放在单个长函数 | 按工具结果、assistant 工具调用、普通消息与轮次合并划分 |
| 控制台主脚本混合模型、统计、日志和启动；部分源码压缩为长行 | 按功能拆分，统一格式；实际页面行为保持回归通过 |
| 静态测试依赖旧脚本文件名和精确空格格式，文档职责表已过时 | 模板提供唯一脚本清单，测试适应格式化，文档同步 |

## 第一轮：拆分责任归属

- 新增 `app/proxies/protocols.py`，集中 URI 分类、校验、脱敏和 outbound 转换。
  `proxy_resolver.py` 保留二进制发现、进程与出口生命周期，公共解析入口显式转导出。
- 新增 `app/upstreams/cookie_transport.py`，承接 HTTP 事件读取、首回复窗口、代理切换、
  工具协议降级和错误分类。Cookie OpenAI、原生桥接与凭证探测直接引用该模块。
- 从控制台主脚本拆出 `console-models.js`、`console-overview.js`、`console-logs.js`、
  `console-bootstrap.js`。日志和概览的内部状态留在所属作用域，启动模块最后加载。
- 锁定开发依赖 Prettier 3.6.2，格式化静态 JavaScript，增加格式化与检查命令。
  Python 运行依赖没有升级；控制台仍使用本地静态资源，无运行时打包要求。

复查发现，仅拆文件仍未解决生成入口的长闭包，因此继续第二轮。
模块移动使部分测试桩仍指向旧所有者；已将传输模拟改为实际所属模块，保留原有行为断言。

## 第二轮：显式请求状态与交付阶段

- `CookieGeneration` 持有一次 Cookie 请求的凭证快照、模型设置、重试参数和计时状态，
  分别提供生图、流式、非流式和缓冲交付方法。凭证校验与设置准备位于独立准备函数。
- `SDKGeneration` 持有当前客户端、模型和回退目标；客户端切换通过实例方法执行，
  真流式与非流式不再依赖入口的嵌套闭包。
- 新增 `app/upstreams/express_response.py`，集中 SDK chunk 转换、工具调用索引、
  预填充与 SSE 分块。`execute_gemini_call()` 的调用签名保持不变。

重试专项回归发现假流式转发时遗漏了 `is_auto_attempt`，已补回并重跑相关测试。
这说明文件能导入或语法检查通过不足以验收，必须覆盖实际交付模式。
复查还发现消息角色转换、静态导出测试和架构文档需要继续整理，进入第三轮。

## 第三轮：转换职责、结构约束与文档

- `create_gemini_prompt()` 改为角色分流与组装入口。工具结果、assistant 工具调用、
  普通消息和相邻轮次合并各自独立；签名、工具结果和 Part 顺序保持原有规则。
- DOM 回归从 HTML 模板读取脚本清单和加载顺序，避免新增脚本后忘记同步测试。
  导出函数检查不再依赖 `Object.assign(window,{` 的具体空白写法。
- 新增 `scripts/check_architecture.py`，接入统一检查入口，检查三个已拆模块的反向依赖
  及应用模块加载时的导入环。兼顾绝对/相对导入；反向依赖检查也覆盖函数内导入。
- 新增 8 个架构检查反例/正例测试，覆盖非法反向依赖、条件导入环、相对包导入环、
  延迟依赖和模块缺失；正常的包内子模块导入也有正例，防止误报自身循环依赖。
- CI 增加 JavaScript 格式检查，更新 README 和 `architecture.md` 的职责表、入口与维护命令。
  清理拆分后失真的注释，将新代码中的复杂条件字典展开改为明确步骤。

## 可核对的结果

以下是入口函数的物理行数，不是项目总代码量；逻辑被拆到明确的处理函数和请求对象，未删除协议分支。

| 入口 | 本轮开始 | 本轮结束 | 内嵌函数数量 |
| --- | ---: | ---: | --- |
| `CookieProxyUpstream.chat_completions` | 733 | 13 | 6 → 0 |
| `execute_gemini_call` | 472 | 36 | 3 → 0 |
| `create_gemini_prompt` | 317 | 28 | 2 → 0 |

格式化会增加许多文件的物理行数，因此没有以文件总行数或 diff 行数作为“更简洁”的证据。
主要收益是修改位置明确、入口易读、请求状态可见、公共模块依赖方向可检查。
针对 Cookie 的 6 个抽取方法和 SDK 的 3 个抽取方法，另做了一次源码 AST 对照：
在归一化 `self` 字段、方法重命名和 `nonlocal` 移除后，原有方法逻辑一致。
这项对照不替代完整回归，也不覆盖所有运行时行为。

## 后续维护边界

三轮后，前述职责与回归标准已满足。仍有较长的协议状态机，例如 SDK 流式输出和 Gemini 原生透传；
继续拆分应围绕实际协议变更和可验证边界进行，不以函数长度阈值机械切割。
控制台也仍保留供 HTML 内联处理器和表单模块使用的全局接口，并未迁移为 ES modules。
架构检查是静态检查，不能推断动态导入和任意运行时调用关系。

新增功能时按 [架构约定](architecture.md) 找到所属模块；修改转换代码运行协议回归，
修改模板或脚本运行 DOM 与浏览器回归。仅需整理前端格式时使用 `npm run format:console`。
